## Concrete problem and bounded improvement

The inspected cmd/server/main.go has approximately184 lines; line count alone is not evidence of a problem. Its `start` function currently acquires a pool/listener, configures logging and middleware, constructs every module, and assembles shutdown/resource ownership in one place. This mixes network/resource ownership with router composition and makes testing the actual middleware/route composition require unnecessary startup work.

Separate those responsibilities inside the existing executable package. Extract a coherent router-construction function/file that installs the existing error handler, middleware and module dependencies without acquiring a listener, starting a server, pinging PostgreSQL or closing caller-owned resources. Keep `start` responsible for pool/listener acquisition, failed-start cleanup, HTTP-server assembly and owned close/shutdown functions. Retain the already-useful `application`/`run` lifecycle seam; place it in a cohesive file if that improves navigation. Keep configuration/process entrypoint logic in main.go unless moving an unchanged function is required for cohesion.

Use concrete collaborators and simple local functions. No generic application container, router registry framework, lifecycle interface hierarchy, mutable test hook or production test endpoint. An explicit existing zerolog.Logger argument can be reasonable for router composition and logging assertions, but preserve normal startup output/global logger behavior. Do not introduce a flag parser abstraction merely to execute main's uncovered lines. Leave CLI flags, signal registration and process exit semantics intact. Replacing the global cfg/config.Get design is R4 scope and must not be included here.

Freshly inspect the merged post-P4/post-R1 tree before editing: module constructor signatures and route counts have changed since preparation. Use the current signatures, not stale P2/P3 examples. Do not restore testcase's removed renderer coupling or obsolete modules.
