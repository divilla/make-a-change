## Current and target contracts

The existing main-screen `/config` presents repository-local `.mch/config.yaml` values (`backend_url`, `project_id`); project-detail `/project-config` reads the selected project's resolved backend catalog. Neither is backend configuration management. Preserve both. Add clearly named, keyboard-reachable backend configuration management and health actions without repurposing local settings or editing `.mch/config.yaml` to manage backend rows. Backend configurations are selected by immutable string slug; there is no project configuration-assignment write in the current project API.

All five configuration operations are POST under `/api/v1/config`:

| Route | Request JSON | Success | Contract |
| --- | --- | --- | --- |
| `/list` | No required fields | `200` array of full configurations | Backend orders rows by slug under its database collation; preserve that returned order without imposing Go lexical order. Empty is `[]`. |
| `/details` | `{"slug":"nonblank"}` | `200` full configuration | Exact supplied slug; no default fallback. |
| `/insert` | Full configuration write | `201 {"slug":"created-slug"}` | New immutable identity; duplicate slug may return `409`. |
| `/update` | Full configuration write | `204` empty | Replaces all six arrays for the existing slug; never renames it. Missing slug returns `404`. |
| `/delete` | `{"slug":"nonblank"}` | `204` empty | A referenced row is rejected atomically with `409 config is in use`; missing slug returns `404`. |

The full read/write fields are `slug`, `project_docs`, `epic_docs`, `change_docs`, `change_phases`, `change_colors`, `change_types`. All six arrays must be present and non-null in writes; each may be `[]`. The backend rejects blank/whitespace-only slug or array members but does not silently trim or deduplicate values. Preserve the exact configured order and values and distinguish explicit empty arrays from omitted/null/malformed arrays. Do not invent a default catalog, array normalization, config assignment endpoint, or rename operation. HTTP 400/404/409 and other failures retain status and underlying cause in typed errors. Each adapter method performs one context-aware finite-timeout request, with exact method, payload, status and response shape; no guessed envelope, alternate route or automatic write retry.

Both health routes are GET with no request body: `/api/v1/health` and `/api/health`. Each returns `200 {"status":"ok","api":"ok","database":"ok"}` when healthy, or `503 {"status":"degraded","api":"ok","database":"error","error":"database unavailable"}` when its database ping fails. Treat a valid degraded `503` body as a displayable diagnostic result while retaining its HTTP status; do not discard it as a generic transport error or claim it is healthy. Reject malformed, contradictory, missing-field or unexpected-status responses, and distinguish transport failures from a valid degraded result. Do not use the health action to start/stop a server or database.
