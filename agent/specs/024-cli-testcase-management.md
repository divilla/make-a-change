## Current and target contracts

The current `pkg/client/http.go` testcase mutations send plausible request keys but call `postChange` and demand a change entity from every response. Backend create actually returns `201 {"id":N}`; update, update-done and delete return `204` with no body. `pkg/client/documents.go` already reads `/api/v1/test-case/list` separately, but its wire projection drops `created_at` and `updated_at`, represents numeric IDs as strings and does not yet prove every current field. The shell still owns testcase forms, validation, commands, write sequencing and results in `internal/app/change_save.go`, `update.go` and `dropdown.go`; `internal/testcases` has placeholder model/API and titles/commands only. Change detail already renders separately read testcase rows. P5 migrates these behaviors to `testcases` while preserving the embedded change-detail entry point and prior P4 behaviors.

All five routes are `POST` under `/api/v1/test-case`. The backend `internal/testcase/api.go`, `service.go`, `repo.go` and `internal/domain/test_case.go` establish these exact contracts:

| Route | Request | Success | Behavior |
| --- | --- | --- | --- |
| `/list` | `{"change_id":positive integer}` | `200` JSON array | Rows have numeric `id`, `change_id`, string `scenario`, boolean `done`, `created_at`, `updated_at`; ordered by ID. Empty is `[]`. |
| `/create` | `{"change_id":positive integer,"scenario":nonblank string}` | `201 {"id":positive integer}` | Backend trims scenario; no change entity. |
| `/update` | `{"id":positive integer,"scenario":nonblank string}` | `204` empty | Edits scenario only; no change entity. |
| `/update-done` | `{"id":positive integer,"done":boolean}` | `204` empty | Explicit `true` and `false` support done and undone. |
| `/delete` | `{"id":positive integer}` | `204` empty | Removes only that testcase. |

The backend has no testcase details or move/change-assignment route. Invalid payloads return 400; missing records may return 404. Preserve HTTP status and underlying cause in typed errors. Each transport method performs one context-aware, finite-timeout request; a successful write needs explicit `/list` and, where completion counters are shown, `/change/details` refresh. No automatic replay of committed writes or recursive envelope/alternate-field parsing.

## Acceptance and required evidence

- **P5-01 — Exact typed HTTP operations.** Implement each of the five route methods with the payload/status/body contracts above. Reject malformed arrays/rows, missing or invalid fields, wrong owner IDs, malformed/missing create IDs, unexpected statuses/bodies, invalid local IDs and canceled requests as errors. Preserve large numeric IDs without float conversion; carry timestamps and `done=false` accurately. Do not infer a change entity from testcase responses. Unit mapping: `TestP501TestCaseRoutesPayloadStatusAndOneRequest`, `TestP501ListFieldsOwnerOrderAndLargeIDs`, `TestP501MalformedTestCaseResponsesAndStatusCauses`, `TestP501CanceledTestCaseRequest`. These tests assert request counts and all fields, not just method names.
- **P5-02 — Reachable testcase lifecycle.** From change details, show the current list and support keyboard/slash create, scenario edit, explicit mark done and undone, confirmed delete, refresh and return. Render scenario, status, identity and timestamps in accessible detail as appropriate, with loading, empty, failure and success feedback. Validate blank/whitespace scenario and IDs before sending, preserve a meaningful draft on failed save, and treat command-shaped scenario text as literal data. Keep selection stable where the ID survives refresh; no cached invisible row may be acted on during reload. Unit mapping: `TestP502TestCaseFormValidationAndLiteralDraft`, `TestP502CreateEditToggleDeleteNavigation`, `TestP502EmptyLoadingErrorAndScrollableDetails`, `TestP502SelectionAfterRefreshAndReloadSafety`. Each named test must drive actual behavior and assert visible state or outbound effects.
- **P5-03 — Testcase feature ownership.** `internal/testcases` owns its model, validation, forms, operation sequencing/results and rendering; a small consumer-owned API interface covers only needed reads/writes. The app shell injects the capability, routes typed messages, composes the change-detail entry point and global navigation. `changes` may display testcase rows and refresh change completion fields, but must not own testcase writes. Preserve architecture import rules and avoid an empty forwarding model or duplicate backend interface. Unit mapping: `TestP503FeatureOwnsTestCaseTransitionsAndMessages`, `TestP503ShellRoutesTestCaseResultWithoutReimplementingMutation`, plus existing `TestCLIPackageBoundaries` and a fixture proving forbidden imports fail.
- **P5-04 — Correct write and read sequencing.** On create, retain returned ID; on every successful mutation, record its committed outcome before refreshing `/test-case/list` and any displayed `/change/details` completion. A later read failure reports “saved/deleted; refresh failed” (or equivalent precise status), offers read-only retry and never repeats the write. Failure before commit leaves the draft/state retryable; no duplicate submission while busy. Stale project/change/op/revision results cannot overwrite current rows, draft, confirmation or feedback. Program shutdown cancels owned work; no `context.Background()` in testcase commands. Unit mapping: `TestP504CommittedTestCaseWriteSurvivesRefreshFailure`, `TestP504FailedWriteRetryAndBusyDeduplication`, `TestP504StaleProjectChangeAndRevisionResults`, `TestP504CanceledTestCaseWorkAndReadOnlyRetry`.
- **P5-05 — Preserve P4 cross-feature behavior.** Separate testcase reads remain part of change-detail loading; row actions update testcase state and then server-provided change completion counters. Do not derive completion from local rows or expect embedded testcases in change response. Preserve change/document editors, selected-project catalogs, search/scrolling and P4 partial-success behavior. Unit mapping: `TestP505ChangeDetailSeparateReadsAndServerCompletion`, `TestP505TestCaseFailureDoesNotCorruptChangeOrDocumentDraft`, plus retained `TestP404StaleResultsCanceledWorkAndInvisibleRows`, `TestP405CommittedStepsSurviveLaterFailureAndRetryOnlyReads` and their program counterparts.
- **P5-06 — Complete-program and PTY evidence.** Extend the existing injected-I/O program driver and fake backend to exercise list/create/edit/done/undone/delete by keyboard, asserting exact requests, visible results, partial success/read-only retry, malformed response and stale selection. Add the new program tests by exact name to `cli/scripts/terminal-scenarios.json` and its inventory assertion. Extend a real PTY scenario with testcase entry, scrolling/redraw and at least one mutation with fake backend. Direct client/model tests, architecture and harness unit tests contribute no terminal counters. Suggested names: `TestCLIProgramTestCaseLifecycle`, `TestCLIProgramTestCaseCommittedWriteAndStaleRecovery`, and `TestShellNavigationEditorAndScrolling` extension or a named PTY child. Unit mapping: `TestP506ScenarioManifestIncludesTestCaseProgramAndPTY` and existing harness/manifest inventory tests. Preserve valuable `TestRetainedTestCaseMutationPayloads` assertions by migrating them to exact target statuses/responses; replace obsolete entity-return assertions explicitly in the ledger.

Each acceptance bullet above requires a meaningful named unit assertion, including every operation and success/failure variant. The names are a contract map; implementation may use equivalent descriptive names if recorded in `cli/agents/cli-contracts.md`.
